# 10. `exception_ptr`, `nested_exception`, конструкторы и деструкторы

**Пункт плана:** 10 — дополнительные темы.

## Что показывает пример

* `std::exception_ptr` + `std::current_exception` / `std::rethrow_exception` —
  перенос исключения из рабочего потока в главный.
* `std::throw_with_nested` / `std::rethrow_if_nested` — цепочка причин.
* Исключение в конструкторе (нормально) и почему нельзя бросать из деструктора.

## Запуск

```bash
./build/10_advanced
```

Ожидаемый вывод: исключение из потока перехватывается в `main`; вложенные
исключения печатаются «причина за причиной»; конструктор с пустым хостом бросает.

## Плохо → Хорошо

**Плохо** — бросать исключение из деструктора:

```cpp
~Buffer() {
    if (!flush_ok) throw std::runtime_error("не удалось сбросить буфер");
}
```

ПОЧЕМУ плохо: если деструктор вызван при раскрутке стека (уже летит другое
исключение), второе исключение приводит к немедленному `std::terminate()`.
К тому же деструкторы неявно `noexcept`, так что выброс из них = аварийное завершение.

**Хорошо** — деструктор не бросает; ошибки сообщаются заранее отдельным методом:

```cpp
void close();           // здесь можно бросить и обработать
~Buffer() noexcept {    // тихо освобождаем, ошибки логируем, но не бросаем
    if (!flush_ok) log("flush failed in dtor");
}
```

ПОЧЕМУ хорошо: ресурс гарантированно освобождается без риска `terminate()`, а
для отчёта об ошибке есть явный метод (`close`/`flush`), который вызывают до
разрушения объекта. Исключения в конструкторах, наоборот, — нормальный способ
сообщить о невозможности построить объект.
