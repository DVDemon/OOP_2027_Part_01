# 10. Инкапсуляция и идиома PIMPL

**Пункт плана:** 10 — принципы инкапсуляции и обзор идиомы PIMPL.

## Что показывает пример

* **Инкапсуляция** — сокрытие реализации за стабильным интерфейсом.
* **PIMPL (Pointer to IMPLementation)**: класс `Widget` хранит только
  `std::unique_ptr<Impl>`, а полное определение `Impl` спрятано в `widget.cpp`.
* Деструктор и move-операции объявлены в `.h`, но **определены в `.cpp`**, где
  тип `Impl` уже полный.

Преимущества PIMPL:

* ускорение компиляции — правка `Impl` не требует перекомпиляции клиентов;
* стабильный ABI — размер `Widget` не зависит от полей `Impl`;
* полное сокрытие деталей реализации из заголовка.

Накладные расходы: дополнительная косвенность (разыменование указателя) и
аллокация `Impl` в куче.

## Сборка и запуск

```bash
cmake -S .. -B ../build       # из папки лекции
cmake --build ../build
./../build/10_encapsulation_pimpl
```

Цели: `10_encapsulation_pimpl` — демонстрация в консоли.

## Плохо → Хорошо

**Плохо (для PIMPL)** — задать деструктор `= default` прямо в заголовке:

```cpp
// widget.h — ПЛОХО
class Widget {
    struct Impl;                   // неполный тип
    std::unique_ptr<Impl> pImpl_;
public:
    Widget();
    ~Widget() = default;           // ОШИБКА: здесь Impl неполон
};
```

**Почему плохо:** чтобы уничтожить `unique_ptr<Impl>`, компилятору нужен **полный**
тип `Impl` (вызов `delete`). В заголовке `Impl` объявлен, но не определён —
будет ошибка компиляции либо неопределённое поведение.

**Хорошо** — объявить деструктор в `.h`, а `= default` поставить в `.cpp`:

```cpp
// widget.h
class Widget {
    struct Impl;
    std::unique_ptr<Impl> pImpl_;
public:
    Widget();
    ~Widget();                    // только объявление
};

// widget.cpp
struct Widget::Impl { /* полное определение */ };
Widget::~Widget() = default;      // здесь Impl уже полный — корректно
```

**Вывод:** при PIMPL все специальные функции, которым нужен полный `Impl`
(деструктор, move-операции), определяйте в `.cpp`, а не в заголовке.
