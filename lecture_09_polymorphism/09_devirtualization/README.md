# 09. Стоимость виртуальных вызовов и девиртуализация

**Пункт плана:** 9 — стоимость виртуальных вызовов и девиртуализация.

## Что показывает пример

* Виртуальный вызов дороже прямого: косвенность (чтение `vptr` → vtable →
  вызов), невозможность инлайнинга, возможный cache miss.
* Когда тип известен статически (или класс/метод помечен `final`), компилятор
  выполняет **девиртуализацию** и может встроить вызов.
* Простое измерение времени через `std::chrono`.

## Запуск

```bash
./build/09_devirtualization
```

> Сравните разницу с `-O2`: на оптимизации прямой вызменяемый цикл часто
> заметно быстрее. Числа зависят от компилятора и железа — это иллюстрация,
> а не бенчмарк.

## Плохо → Хорошо

**Плохо** — делать `virtual` всё подряд «на всякий случай» в горячем коде:

```cpp
class Vec3 {
public:
    virtual double dot(const Vec3&) const;   // virtual в тяжёлой математике
};
// Каждый вызов в цикле — косвенный, инлайнинг невозможен.
```

**Хорошо** — `virtual` только там, где реально нужен полиморфизм; для
закрытых иерархий помогать компилятору через `final`:

```cpp
class Vec3 { public: double dot(const Vec3&) const; };  // не virtual — обычный inline

class Fast final : public Base {            // final -> девиртуализация
public:
    int compute(int x) const override;
};
```

**Почему:** полиморфизм — инструмент с ценой. Виртуальность нужна для
позднего связывания; если оно не требуется, обычная функция инлайнится и
работает быстрее. `final` сообщает компилятору, что переопределений не будет,
и тот может заменить косвенный вызов прямым.
