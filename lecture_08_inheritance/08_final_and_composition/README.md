# 08. `final` и «предпочитайте композицию наследованию»

**Пункт плана:** 8.

## Что показывает пример

* `final` у класса: от `Framework` нельзя наследоваться.
* `final` у виртуального метода: `process()` нельзя переопределить.
* Композицию вместо наследования для отношения has-a: `Car` содержит `Engine`.
* LSP-ловушку `Circle : Ellipse` (в комментарии).

## Запуск

```bash
./build/08_final_and_composition
```

## Плохо → Хорошо

**Плохо** — наследовать ради переиспользования кода:

```cpp
class Car : public Engine {};   // машина НЕ является двигателем
```

**Хорошо** — композиция:

```cpp
class Car {
    Engine engine_;             // машина СОДЕРЖИТ двигатель
};
```

**Почему:** public-наследование означает is-a и обязывает проходить тест
Лисков. `Car` не подставляется вместо `Engine`, поэтому наследование здесь
семантически неверно.

## Когда наследование уместно

1. Отношение is-a проходит тест Лисков (LSP).
2. Нужен полиморфизм через виртуальные функции.
3. Базовый класс спроектирован для наследования (есть виртуальный деструктор,
   документированные точки расширения).

## Ключевая мысль

`final` — инструмент ограничения иерархии: он фиксирует, что дальше
расширять тип нельзя, и помогает компилятору. Композиция — инструмент
выбора связи: она слабее наследования и почти всегда предпочтительнее,
если отношение не является is-a.
