# 12. Примеси, интерфейсы и альтернативы MI

**Пункт плана:** 12.

## Что показывает пример

Четыре подхода к одной задаче «многофункциональное устройство»:

| Вариант | Класс | Отношение |
|---|---|---|
| A. MI от конкретных классов | `MfpInherited` | is-a к каждому устройству |
| B. Композиция | `MfpComposed` | has-a, делегирование |
| C. Примеси без шаблонов | `Button : Clickable, Hoverable` | добавление поведения |
| D. Чистые интерфейсы | `SmartDevice : IPrintable, IScannable` | реализация контрактов |

* Примеси здесь — обычные классы без данных и без шаблонов; ромба не
  возникает, потому что общей базы нет.
* Композиция предпочтительна, когда устройство **владеет** подсистемами.
* MI от интерфейсов безопасно: у них нет данных и состояния.

## Запуск

```bash
./build/12_mixins_and_alternatives
```

## Когда множественное наследование оправдано

| Ситуация | Рекомендация |
|---|---|
| Один основной класс + интерфейсы без данных | безопасно, используйте |
| Независимые примеси поведения | безопасно, если нет общей базы |
| Два «больших» класса с данными | избегайте — нужна композиция |
| Ромб без `virtual` | почти всегда ошибка |

**Правило:** если вы задумались о MI от классов с данными — скорее всего,
нужна композиция.

## Альтернативы

1. **Композиция** — владение и делегирование.
2. **Чистые интерфейсы** — несколько независимых контрактов без данных.
3. **Примеси** — маленькие классы поведения, подмешиваемые наследованием.

## Ключевая мысль

MI безопасно тогда, когда базы не делят состояние: интерфейсы, примеси,
безданные «теги». Как только у баз появляются данные и общий предок,
множественное наследование превращается в управление структурой объекта —
и почти всегда проигрывает композиции.
