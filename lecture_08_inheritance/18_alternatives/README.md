# 08. Альтернативы: композиция и чистые интерфейсы

**Пункт плана:** 8 — альтернативы множественному наследованию.

## Что показывает пример

* **Композицию**: `Mfp` (Multi-Function Peripheral) не наследует
  `Printer`/`Scanner`/`Fax`, а владеет ими как полями и делегирует вызовы.
* **Чистые интерфейсы**: множественное наследование от классов без данных
  (`IPrintable`, `IScannable`) — безопасный и распространённый приём.

## Запуск

```bash
./build/08_alternatives
```

Ожидаемый вывод:

```
=== Композиция (Mfp владеет Printer/Scanner/Fax) ===
[PRINT] Отсканированный документ
[FAX] отправлено: Отсканированный документ

=== Чистые интерфейсы ===
Печать...
Документ отсканирован
```

## Плохо → Хорошо

**Плохо** — наследоваться сразу от нескольких «толстых» классов с данными:

```cpp
class Mfp : public Printer, public Scanner, public Fax { /* ... */ };
// риск ромба (если у них общий предок), дублирование данных,
// жёсткая связанность, неоднозначность имён
```

**Хорошо** — композиция (владение) вместо наследования:

```cpp
class Mfp {
    Printer printer_;
    Scanner scanner_;
    Fax     fax_;
public:
    void print(const std::string& d) const { printer_.print(d); }
    // делегируем — связь слабая, ромба нет
};
```

…и множественное наследование **только** от интерфейсов:

```cpp
class SmartDevice : public IPrintable, public IScannable { /* override... */ };
```

**Почему:** классы с данными при множественном наследовании дают ромб,
дублирование полей и неоднозначность. Композиция выражает отношение
«has-a» явно, оставляет связь слабой и легко заменяемой. Интерфейсы же не
содержат состояния, поэтому наследование от многих интерфейсов не создаёт ни
ромба данных, ни дублирования — это нормальная и рекомендуемая практика
(как `implements` в Java).
