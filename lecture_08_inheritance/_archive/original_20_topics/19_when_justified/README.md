# 09. Когда множественное наследование оправдано

**Пункт плана:** 9 — когда множественное наследование оправдано.

## Что показывает пример

* «Золотой» сценарий MI: **один основной (полиморфный) класс** `GameObject`
  плюс **несколько чистых интерфейсов** `IDrawable`, `ICollidable` (как в Java).
* Работу с объектом через любой из контрактов и однородные коллекции по
  интерфейсу.

## Когда MI оправдано

| Ситуация | Рекомендация |
|---|---|
| Наследование от нескольких интерфейсов | Безопасно, используйте |
| Один основной класс + интерфейсы | Нормально (как в Java) |
| Mixin-классы (CRTP) | Хорошая практика |
| Два «больших» класса с данными | Избегайте — используйте композицию |
| Diamond без `virtual` | Почти всегда ошибка |

## Плохо → Хорошо

**Плохо** — собирать сущность из нескольких классов **с данными**:

```cpp
class Player : public GameObject, public PhysicsBody, public Sprite {};
// если у баз есть общий предок -> ромб; если нет -> всё равно дублирование
// состояния и жёсткая связанность реализаций
```

**Хорошо** — один основной класс с состоянием + чистые интерфейсы-контракты:

```cpp
class Player : public GameObject,        // единственный класс с данными
               public IDrawable,         // чистый интерфейс
               public ICollidable {};    // чистый интерфейс
```

**Почему:** правило простое — если задумались о множественном наследовании от
классов **с данными**, скорее всего нужна композиция. Один класс-носитель
состояния плюс несколько интерфейсов даёт гибкость полиморфизма без проблемы
ромба, дублирования данных и неоднозначности имён.
