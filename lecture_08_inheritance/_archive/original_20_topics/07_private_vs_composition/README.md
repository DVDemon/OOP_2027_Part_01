# 07. Приватное наследование vs композиция

**Пункт плана:** 7.

## Что показывает пример

* Класс `Stack`, реализованный через **композицию** поверх `std::vector<int>`.
* Полное сокрытие интерфейса `vector`: наружу видны только операции стека.

## Сборка и запуск

```bash
cmake -S .. -B ../build       # из папки лекции
cmake --build ../build
./../build/07_private_vs_composition
```

Цели: `07_private_vs_composition` — демонстрация в консоли.

## Плохо → Хорошо

**Плохо** — приватное наследование от контейнера ради переиспользования реализации:

```cpp
class Stack : private std::vector<int> {
public:
    void push(int v) { push_back(v); }
    // ...
};
```

Это работает, но крепко привязывает `Stack` к типу `std::vector`, открывает
наследнику весь protected/public-интерфейс vector и усложняет замену контейнера.

**Хорошо** — композиция: контейнер как закрытое поле:

```cpp
class Stack {
    std::vector<int> data_;        // деталь реализации
public:
    void push(int v) { data_.push_back(v); }
    // ...
};
```

**Почему:** композиция даёт более слабую связь, явный контроль над интерфейсом и
свободу заменить `std::vector` на `std::deque` без изменения публичного API.
Приватное наследование оправдано лишь когда нужен доступ к `protected`-членам базы,
переопределение её виртуальных функций или оптимизация пустого базового класса (EBO).
