# 10. Практические рекомендации

**Пункт плана:** 10 — практические рекомендации.

## Что показывает пример

На материале практического задания лекции (`Character` → `Warrior`, `Mage` →
`BattleMage`) показаны **оба** подхода:

* **Вариант А** — виртуальное наследование: корректное решение ромба, если
  множественное наследование действительно необходимо. `BattleMage` —
  most-derived класс — сам вызывает конструктор виртуальной базы `Character`.
* **Вариант Б** — композиция (`BattleMageComposed`): предпочтительная
  альтернатива наследованию от классов с данными.

## Запуск

```bash
./build/10_recommendations
```

Ожидаемый вывод:

```
=== Вариант А: виртуальное наследование ===
Gandalf бьёт с силой 7
Gandalf читает заклинание (мана 50)
Gandalf: hp=100, level=10

=== Вариант Б: композиция (рекомендуется) ===
Merlin бьёт с силой 6
Merlin читает заклинание (мана 60)
```

## Свод рекомендаций

* Множественное наследование от **интерфейсов** — нормальная практика.
* **Виртуальное наследование** добавляет накладные расходы (`vbptr`, косвенный
  доступ) — применяйте только при необходимости.
* Помните: **most-derived** класс отвечает за вызов конструктора виртуальной базы.
* Не используйте `reinterpret_cast` в иерархиях MI — он не корректирует указатели.
* Тестируйте преобразования указателей, если используете MI с данными.
* Предпочитайте **CRTP-mixins** и **композицию** классическому MI.

## Плохо → Хорошо

**Плохо** — ромб без `virtual` для класса с данными:

```cpp
class Warrior : public Character { /* ... */ };  // нет virtual
class Mage    : public Character { /* ... */ };  // нет virtual
class BattleMage : public Warrior, public Mage {};
// -> ДВА Character: hp/level дублируются, bm.hp() неоднозначно
```

**Хорошо** — либо `virtual` (если MI оправдано), либо композиция (по умолчанию):

```cpp
// А) виртуальное наследование
class Warrior : virtual public Character { /* ... */ };
class Mage    : virtual public Character { /* ... */ };
class BattleMage : public Warrior, public Mage {
    BattleMage(...) : Character(...), Warrior(...), Mage(...) {}  // most-derived
};

// Б) композиция (предпочтительно)
class BattleMageComposed {
    Character base_;
    int strength_, mana_;
};
```

**Почему:** ромб без `virtual` даёт две копии `Character`, дублирование `hp`/
`level` и неоднозначность. `virtual` решает это ценой накладных расходов и
требует явного вызова конструктора базы из most-derived класса. Композиция же
не порождает ромба вовсе, оставляет связь слабой и обычно проще в сопровождении —
поэтому она и есть рекомендуемый выбор по умолчанию.
