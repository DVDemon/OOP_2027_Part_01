# 10. Резюме: `DynamicArray` и правило пяти

**Пункт плана:** 10 — резюме и связь с правилом пяти.

## Что показывает пример

Класс `DynamicArray` собирает воедино конструкторы из лекции:

* конструктор по умолчанию (пустой массив);
* `explicit DynamicArray(std::size_t capacity)`;
* делегирующий `DynamicArray(count, value)` -> `DynamicArray(capacity)`;
* конструктор из `std::initializer_list<int>`;
* копирующий конструктор — **глубокая** копия;
* деструктор — освобождение `new[]`.

Перемещение и присваивание помечены `=delete` — их полная реализация требует
**правила пяти** (тема следующей лекции).

## Правило пяти

Если класс управляет ресурсом (память, файл, сокет), продумайте все пять
специальных методов:

1. деструктор;
2. копирующий конструктор;
3. копирующий оператор присваивания;
4. перемещающий конструктор;
5. перемещающий оператор присваивания.

## Плохо → Хорошо

**Плохо** — определить деструктор с `delete[]`, но положиться на
сгенерированный копирующий конструктор:

```cpp
DynamicArray a{1, 2, 3};
DynamicArray b = a;   // поверхностная копия: b.data_ == a.data_
// при разрушении a и b -> двойное delete[] -> UB
```

**Хорошо** — реализовать глубокую копию (а недостающие операции явно
запретить, пока не реализованы корректно):

```cpp
DynamicArray(const DynamicArray& other)
    : data_(new int[other.capacity_]{}), size_(other.size_),
      capacity_(other.capacity_) {
    std::copy(other.data_, other.data_ + other.size_, data_);
}
DynamicArray(DynamicArray&&) = delete;            // пока не реализовано
DynamicArray& operator=(const DynamicArray&) = delete;
```

**Почему:** наличие ручного деструктора — сигнал, что класс владеет ресурсом.
Тогда автогенерированная (поверхностная) копия почти наверняка некорректна:
два объекта разделят один указатель и оба попытаются его освободить. Глубокая
копия даёт каждому объекту собственный буфер; `=delete` для ещё не реализованных
операций превращает потенциальный UB в ошибку компиляции.
