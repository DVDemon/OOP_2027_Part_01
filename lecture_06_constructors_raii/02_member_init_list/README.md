# 02. Member Initializer List и порядок инициализации

**Пункт плана:** 2 — MIL и порядок инициализации.

## Что показывает пример

* `const`-поле (`id_`) и ссылка (`group_ref_`) инициализируются **только**
  через MIL.
* Реальный порядок инициализации полей определяется **порядком их объявления**
  в классе, а не порядком записей в списке инициализации.
* Класс `Ordered` печатает порядок инициализации: несмотря на запись
  `c_, b_, a_` в MIL, поля инициализируются `a_, b_, c_`.

## Запуск

```bash
./build/02_member_init_list
```

## Плохо → Хорошо

**Плохо** — пытаться присвоить `const`-поле/ссылку в теле конструктора:

```cpp
Student(int id, std::string& group) {
    id_ = id;            // ОШИБКА: присваивание const
    group_ref_ = group;  // ОШИБКА: ссылку нельзя «переназначить»
}
```

**Хорошо** — инициализировать через MIL:

```cpp
Student(int id, std::string& group) : id_(id), group_ref_(group) {}
```

**Почему:** к моменту входа в тело конструктора все поля уже должны быть
проинициализированы. `const`-поле и ссылку нельзя изменить после инициализации,
поэтому единственное место задать им значение — MIL.

**Ловушка порядка:**

```cpp
class Danger {
    int b_;
    int a_;
public:
    Danger(int x) : a_(x), b_(a_) {}  // UB: b_ объявлено первым,
};                                    // значит b_ инициализируется из ещё
                                      // не инициализированного a_
```

**Почему:** компилятор инициализирует поля в порядке объявления (`b_`, затем
`a_`), игнорируя порядок в MIL. Чтобы избежать сюрпризов, записывайте MIL в том
же порядке, что и объявления (компилятор предупреждает флагом `-Wreorder`).
