# 04. Алгоритм разрешения перегрузки

**Пункт плана:** 4.

## Что показывает пример

Компилятор выбирает перегрузку в три этапа:

1. **Множество кандидатов** — все функции с подходящим именем в области видимости.
2. **Фильтрация** — удаляются те, к которым аргументы не подходят даже с преобразованиями.
3. **Ранжирование** — выбирается «наилучшее совпадение» по приоритету преобразований.

### Приоритет преобразований (лучшее → худшее)

1. **Точное совпадение** (включая trivial conversions: массив→указатель и т.п.).
2. **Promotion**: `short`→`int`, `float`→`double`, `bool`/`char`→`int`.
3. **Стандартное преобразование**: `int`↔`double`, указатели в иерархии.
4. **Пользовательское преобразование** (конструкторы/операторы приведения).

Если несколько кандидатов одинаково хороши — **ошибка компиляции** (ambiguity).

## Запуск

```bash
./build/04_overload_resolution
```

## Плохо → Хорошо

**Плохо** — набор перегрузок, порождающий неоднозначность:

```cpp
void foo(int);
void foo(long);
foo(42u);   // ОШИБКА: unsigned int одинаково «далёк» от int и от long
```

ПОЧЕМУ плохо: для `unsigned int` обе перегрузки требуют равноценного
стандартного преобразования. Ни одна не лучше — компилятор не может выбрать и
выдаёт ambiguity. Такой код хрупок: добавление перегрузки легко ломает вызовы.

**Хорошо** — добавить точное совпадение или явно привести тип на месте вызова:

```cpp
void foo(int);
void foo(long);
void foo(unsigned int);   // точное совпадение для 42u

// либо без новой перегрузки — явное приведение:
foo(static_cast<long>(42u));
```

ПОЧЕМУ хорошо: точное совпадение всегда побеждает преобразования, поэтому выбор
становится однозначным. Явный `static_cast` делает намерение видимым в коде и
убирает зависимость от тонкостей ранжирования.
