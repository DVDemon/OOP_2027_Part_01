# 06. `inline`-функции и `constexpr`-функции

**Пункт плана:** 6.

## Что показывает пример

* `inline`-функция `square` — её роль в современном C++ (правила ODR/линковки).
* `constexpr`-функции `factorial` и `fibonacci` — вычисление на этапе компиляции,
  проверка через `static_assert`.
* Одна и та же `constexpr`-функция вызывается и compile-time, и в рантайме.

## `inline` vs `constexpr`

| | `inline` | `constexpr` |
|---|----------|-------------|
| Главная роль | определение в заголовке без нарушения ODR | вычислимость на этапе компиляции |
| Влияет на встраивание? | лишь подсказка (компилятор решает сам) | нет |
| Можно в `static_assert`/размере массива? | нет | да (с constexpr-аргументами) |

## Плохо → Хорошо

**Плохо** — макрос вместо функции «для скорости»:

```cpp
#define SQUARE(x) ((x) * (x))
int y = SQUARE(++a);   // разворачивается в ((++a) * (++a)) — UB!
```

ПОЧЕМУ плохо: макрос — текстовая подстановка без типов и без вычисления
аргумента один раз. `SQUARE(++a)` дважды инкрементирует `a` (неопределённое
поведение), нет проверки типов, ломается отладка.

**Хорошо** — `inline`/`constexpr`-функция:

```cpp
constexpr int square(int x) { return x * x; }
int y = square(++a);   // ++a вычисляется один раз, проверка типов есть
static_assert(square(5) == 25);   // ещё и compile-time
```

ПОЧЕМУ хорошо: настоящая функция вычисляет аргумент один раз, проверяет типы и
видна отладчику. `constexpr` даёт бонус — вычисление на этапе компиляции, а
`inline` снимает overhead вызова там, где компилятор сочтёт нужным.
