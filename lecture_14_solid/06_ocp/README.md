# 06. OCP — принцип открытости/закрытости

**Пункт плана:** 6 — OCP.

> «Программные сущности должны быть открыты для расширения, но закрыты для
> модификации» — Бертран Мейер.

## Что показывает пример

Расчёт суммарной площади фигур через полиморфизм. Функция `total_area()`
**закрыта для модификации**, а иерархия `Shape` **открыта для расширения**:
добавление `Triangle` не требует трогать существующий код.

## Сборка и запуск

```bash
cmake -S .. -B ../build       # из папки лекции
cmake --build ../build
./../build/06_ocp
```

## Плохо → Хорошо

**Плохо** — ветвление по типу фигуры:

```cpp
double calculate(const Shape& shape) {
    if (shape.type == "circle")    return 3.14159 * shape.r * shape.r;
    else if (shape.type == "rect") return shape.w * shape.h;
    // новый тип => правим этот метод (и все похожие)
}
```

**Почему плохо:** каждая новая фигура требует модификации функции `calculate`
(и любой другой, разбирающей тип). Растёт риск регрессий, нарушается
закрытость для модификации.

**Хорошо** — виртуальный метод `area()`:

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

double total_area(const std::vector<std::unique_ptr<Shape>>& shapes) {
    double sum = 0;
    for (const auto& s : shapes) sum += s->area();
    return sum;   // никогда не меняется при добавлении фигур
}
```

**Почему хорошо:** новое поведение добавляется новым классом-наследником.
Существующий код не трогаем — он закрыт для модификации, но открыт для
расширения. OCP опирается на LSP: подтипы обязаны корректно подставляться.
