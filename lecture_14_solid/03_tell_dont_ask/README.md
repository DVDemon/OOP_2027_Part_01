# 03. Tell, Don't Ask (TDA)

**Пункт плана:** 3 — принцип Tell, Don't Ask.

## Что показывает пример

Принцип: **не спрашивай объект о его состоянии, чтобы принять решение, — скажи
ему, что делать.** Вся бизнес-логика, проверяющая инварианты заказа, живёт
внутри `Order`, а вызывающий код просто отдаёт команду `order.ship(wh)`.

## Сборка и запуск

```bash
cmake -S .. -B ../build       # из папки лекции
cmake --build ../build
./../build/03_tell_dont_ask
```

## Плохо → Хорошо

**Плохо** — вызывающий код «допрашивает» объект:

```cpp
void process_order(Order& order, Warehouse& wh) {
    if (order.get_status() == Status::Paid) {   // Ask
        if (order.get_total() > 0) {             // Ask
            order.set_status(Status::Shipped);   // Tell (но поздно)
            wh.ship(order.get_items());
        }
    }
}
```

**Почему плохо:** правила отгрузки размазаны по вызывающему коду. Если бизнес-
правило изменится (например, добавится проверка адреса), править придётся
каждое такое место. Геттеры/сеттеры раскрывают внутреннее состояние и ломают
инкапсуляцию.

**Хорошо** — объект сам отвечает за свои инварианты:

```cpp
void Order::ship(Warehouse& wh) {
    if (status_ != Status::Paid || total_ <= 0.0)
        throw std::logic_error("Нельзя отгрузить неоплаченный заказ");
    wh.ship(items_);
    status_ = Status::Shipped;
}
```

**Почему хорошо:** правило хранится в одном месте — внутри `Order`. Клиент не
знает деталей состояния и не может перевести объект в некорректное состояние.
Изменение правила локализовано.
