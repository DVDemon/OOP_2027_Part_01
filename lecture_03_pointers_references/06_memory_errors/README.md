## Плохо → Хорошо

### Dangling pointer (висячий указатель)

**Плохо:**

```cpp
int* create_value() {
    int local = 42;
    return &local;   // local уничтожается при выходе -> висячий указатель
}

int* p = new int(42);
delete p;
*p = 10;             // UB: use-after-free
```

**Хорошо:** возвращать значение; после `delete` обнулять указатель.

```cpp
int make_value() { int local = 42; return local; }  // по значению
delete p; p = nullptr;                               // защита от use-after-free
```

### Memory leak (утечка памяти)

**Плохо:**

```cpp
void leak(bool flag) {
    int* p = new int(42);
    if (flag) return;   // утечка: delete не вызван на этом пути
    delete p;
}
```

**Хорошо:** освобождать на всех путях (или довериться RAII/контейнеру).

```cpp
void ok(bool /*flag*/) {
    int* p = new int(42);
    // ... ровно один delete на всех путях выхода ...
    delete p;
}
// Ещё лучше: std::unique_ptr<int> p = std::make_unique<int>(42);  (освободится сам)
```

### Double free (двойное освобождение)

**Плохо:**

```cpp
int* p = new int(42);
int* q = p;     // два указателя на одну память
delete p;
delete q;       // UB: двойное освобождение
```

**Хорошо:** один владелец — одно освобождение; чужие указатели не владеют.

```cpp
int* p = new int(42);
delete p; p = nullptr;
// совместное владение -> std::shared_ptr (позже в курсе)
```

**Почему:** ручное управление памятью требует, чтобы у каждого блока был ровно один владелец,
освобождающий его ровно один раз и не использующий после `delete`. Эти инварианты легко нарушить —
поэтому в реальном коде используют RAII (контейнеры, умные указатели), а на этапе разработки — санитайзеры.
